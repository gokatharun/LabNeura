# 1. Executive Summary

LabNeura is a C++-based numerical computing library with a Python interface implemented using pybind11.

The project aims to provide a high-performance, extensible Tensor computing foundation, supporting multiple CPU architectures through backend-specific implementations.

The current architecture separates:

1. Tensor abstraction and memory management.
2. Tensor operations and numerical semantics.
3. Hardware-specific execution backends.

The existing CPU backends are:

- Generic — portable reference implementation.
- NEON — ARM SIMD implementation.
- AVX2 — x86 SIMD implementation.

The library has progressed beyond a simple one-dimensional numerical array implementation. It now has an n-dimensional Tensor foundation, shared storage, strides, offsets, views, broadcasting metadata, arithmetic operations, Boolean dtype support, and comparison operations.

However, LabNeura is still under active development. It is not yet a complete NumPy replacement, general-purpose scientific computing library, or machine learning framework.

The immediate development objective is to complete and stabilize the essential Tensor functionality before expanding into advanced numerical operations, GPU execution, and machine learning capabilities.

# 2. Project Vision

The long-term vision is to develop LabNeura into an extensible numerical computing library with:

- Generalized n-dimensional Tensor abstraction.
- Efficient CPU execution.
- Multiple hardware-specific backends.
- SIMD and multithreaded execution.
- Broadcasting and advanced Tensor operations.
- Matrix and linear algebra operations.
- Numerical and mathematical functions.
- Python interoperability.
- Future GPU acceleration.
- Future automatic differentiation and machine learning capabilities.

The development philosophy is to establish correct, reusable Tensor semantics first, followed by optimized backend implementations.

Generic should serve as the semantic reference. NEON and AVX2 should implement the same behavior using their respective hardware capabilities.

# 3. High-Level Architecture

LabNeura follows a layered architecture.

## 3.1 Python Interface

The Python interface exposes LabNeura functionality through pybind11.

Its responsibilities include:

- Python-facing Tensor construction.
- Python method exposure.
- Conversion between Python and C++ data representations.
- Returning Tensor operation results to Python.

Current limitations:

- Python sequence construction involves copying data into C++ storage.
- Tensor data access returns copied flat Python lists.
- Zero-copy Python interoperability is not implemented.
- Tensor operations do not currently release the Python GIL.

## 3.2 C++ Tensor API

The Tensor layer is responsible for:

- Tensor construction.
- Shape management.
- Dtype management.
- Storage ownership.
- Strides and offsets.
- Views and slicing.
- Broadcasting integration.
- Operation dispatch.
- Output Tensor creation.

The Tensor layer should remain independent of individual SIMD instruction implementations.

## 3.3 Backend Dispatch

LabNeura uses CPU backend detection and runtime selection.

Current backends:

| Backend | Architecture | Purpose |
|---|---|---|
| Generic | Portable CPU | Reference implementation |
| NEON | ARM | ARM SIMD execution |
| AVX2 | x86 | AVX2 SIMD execution |

The project supports runtime backend detection and explicit backend selection through `LABNEURA_BACKEND`.

Unsupported backend requests should fail clearly rather than silently falling back to another backend.

## 3.4 Backend Execution

Each backend contains hardware-specific operation implementations.

The intended separation is:

- Tensor API defines the operation.
- Tensor metadata determines shape and memory layout.
- Backend dispatch selects the implementation.
- Backend kernel executes the operation.

This separation is an important foundation for future hardware extensions.

# 4. Tensor Architecture

The Tensor abstraction is the central component of LabNeura.

A Tensor is a multidimensional collection of elements with associated metadata and storage.

## 4.1 Tensor Dimensions

The current Tensor foundation supports:

| Tensor type | Example shape |
|---|---|
| Scalar / 0D | `[]` |
| Vector / 1D | `[6]` |
| Matrix / 2D | `[2, 3]` |
| 3D Tensor | `[2, 3, 4]` |
| Higher-dimensional Tensor | Arbitrary valid shape |

The existing 1D API is preserved for compatibility.

The nD construction API supports flat data and shape information.

## 4.2 Tensor Components

A Tensor logically contains the following information:

### Storage

The underlying allocated memory containing Tensor elements.

The shared TensorStorage control block manages:

- Memory allocation.
- Ownership and lifetime.
- Dtype.
- Logical element count.
- Allocation capacity.
- Alignment.
- Deallocation.

### Shape

Describes the size of each dimension.

Example:

`[2, 3]`

This represents two rows and three columns.

### Strides

Describes how many elements to move in storage when moving along each dimension.

For a contiguous row-major Tensor with shape `[2, 3]`:

`[3, 1]`

### Offset

Represents the starting position of the logical Tensor within its underlying storage.

### Dtype

Defines the element representation.

### Backend

Determines which supported execution implementation is used for operations.

The conceptual storage-index calculation is:

`storage_index = offset + sum(index[i] * stride[i])`

Strides are measured in elements, not bytes.

## 4.3 Supported Dtypes

The current dtype foundation includes:

| Dtype | Representation | Description |
|---|---|---|
| FP32 | 32-bit floating point | General numerical computation |
| FP16 | 16-bit floating point | Reduced-precision computation |
| INT16 | 16-bit signed integer | Integer computation |
| INT8 | 8-bit signed integer | Compact integer computation |
| BOOL | 8-bit unsigned storage | Canonical Boolean values 0 and 1 |

BOOL is a dedicated dtype rather than an alias for INT8.

## 4.4 Memory Safety

Implemented memory-safety work includes:

- Checked allocation-size calculations.
- Checked alignment rounding.
- Overflow validation.
- Safe zero-size allocation behavior.
- Explicit logical element counts.
- Separation of logical size and allocation capacity.
- Shared storage lifetime management.

SIMD kernels must respect logical element counts rather than assuming padded allocation capacity contains valid Tensor elements.

# 5. Tensor Manipulation Capabilities

## 5.1 Construction

Implemented:

## 5.2 Reshape

Implemented.

Current behavior follows deep-copy semantics.

## 5.3 Flatten

Implemented.

Flatten converts a Tensor into a one-dimensional representation.

Current behavior follows deep-copy semantics.

## 5.4 Shared-Storage Views

Implemented:

- Shared TensorStorage.
- Per-Tensor shape.
- Per-Tensor strides.
- Per-Tensor offset.
- Reshape views.
- First-axis slicing.
- First-axis selection.
- Nested views.
- Storage lifetime management.

Copy, reshape, and flatten retain independent deep-copy semantics.

General arbitrary strided indexing and transpose remain future work.

# 6. Broadcasting Architecture

Broadcasting metadata planning has been implemented.

The planner is a pure metadata component. It calculates:

- Result shape.
- Effective input strides.
- Dimension alignment.
- Broadcast compatibility.
- Output element count.
- Overflow conditions.

It supports:

- Right-aligned dimensions.
- Scalar Tensors.
- Missing leading dimensions.
- Dimensions of size one.
- Zero-sized dimensions.
- Incompatible shape detection.

Broadcasting avoids physically duplicating input data.

A broadcasted dimension can use an effective stride of zero.

For example:

Input A shape: `[2, 3]`

Input B shape: `[3]`

Result shape: `[2, 3]`

B's effective broadcast strides: `[0, 1]`

This allows the same B values to be reused for both rows.

Important distinction:

The broadcasting planner is implemented, but not every backend has native broadcasting kernels.

Current Generic broadcasting arithmetic has been implemented for FP32, FP16, INT8 and INT16.

SIMD broadcasting for NEON and AVX2 remains future work.

# 7. Arithmetic Operations

The four basic arithmetic operations are:

- ADD
- SUB
- MUL
- DIV

Both allocating and in-place operation styles are supported.

Allocating operations produce independent output storage.

In-place operations modify the destination Tensor, subject to the defined shape and aliasing constraints.

## 7.1 Numerical Semantics

The agreed numerical behavior is:

| Dtype | ADD/SUB/MUL | DIV |
|---|---|---|
| FP32 | IEEE floating-point behavior | IEEE floating-point behavior |
| FP16 | FP32 intermediate and conversion back to binary16 | FP32 intermediate and conversion back to binary16 |
| INT16 | Saturating arithmetic | Truncation toward zero |
| INT8 | Saturating arithmetic | Truncation toward zero |

Additional integer division rules:

- Division by zero returns zero.
- Signed minimum divided by negative one saturates to the maximum representable value.

FP16 conversion uses round-to-nearest-even.

The FP16 division contract does not guarantee exact correctly rounded binary16 results for every possible input pair.

## 7.2 Backend Coverage

Generic arithmetic broadcasting is implemented for FP32, FP16, INT8 and INT16.

SIMD arithmetic implementations exist for supported equal-shape paths.

Native NEON and AVX2 broadcasting arithmetic remains a separate future milestone.

# 8. Boolean Dtype and Comparison Operations

## 8.1 BOOL Dtype

## 8.2 Comparison API

The following six operations are defined:

- `eq`
- `ne`
- `lt`
- `le`
- `gt`
- `ge`

Supported comparison input dtypes:

- FP32
- FP16
- INT16
- INT8

Output dtype:

- BOOL

Comparison behavior includes:

- Broadcasting.
- Scalar Tensor handling.
- Zero-sized outputs.
- Offset views.
- Numeric FP16 comparison.
- IEEE NaN semantics.
- Signed-zero semantics.
- Independent output storage.

Mixed-dtype comparisons and BOOL input comparisons are not currently part of the implemented comparison contract.

# 9. CPU Execution and SIMD

## 9.1 Generic Backend

Generic is the portable reference implementation.

It is used to define expected behavior and validate optimized implementations.

## 9.2 NEON Backend

NEON provides ARM SIMD execution.

The Apple Silicon development environment supports local NEON validation.

## 9.3 AVX2 Backend

AVX2 provides x86 SIMD execution using 256-bit vectors.

The Apple Silicon development host cannot execute AVX2 instructions.

Actual AVX2 runtime validation must therefore use an AVX2-capable x86_64 CI runner.

## 9.4 SIMD Widths

Typical vector capacities:

| Dtype | NEON 128-bit | AVX2 256-bit |
|---|---:|---:|
| FP32 | 4 elements | 8 elements |
| FP16 | 8 elements | 16 elements |
| INT16 | 8 elements | 16 elements |
| INT8 | 16 elements | 32 elements |

These are hardware vector capacities, not guarantees that every operation uses the full vector width.

# 10. CPU Threading

A persistent CPU threading foundation has been implemented.

Features include:

- Thread-count query.
- Thread-count configuration.
- Automatic thread-count selection.
- Persistent worker pool.
- Parallel execution support.
- Nested synchronous execution handling.
- Exception propagation.
- Concurrent submission handling.
- Default single-thread behavior.

Parallel FP32 ADD was implemented for Generic and NEON with:

- Parallel threshold: 1,000,000 elements.
- Grain size: 16,384 elements.

Not every Tensor operation currently uses multithreading.

SIMD and multithreading are separate execution mechanisms and can eventually be combined.

# 11. Python Integration

Python integration uses pybind11.

Current behavior:

- Python-facing Tensor API.
- Construction from Python sequences.
- C++ Tensor execution.
- Python result access.
- Python backend detection and configuration.

Current limitations:

- Construction copies input data.
- Data access returns copied Python lists.
- Zero-copy NumPy interoperability is not implemented.
- GIL release around Tensor operations is not implemented.

# 16. Engineering Principles

The following principles should guide future LabNeura development.

1. Generic is the semantic reference.
2. NEON and AVX2 must implement consistent semantics.
3. No silent backend fallback.
4. Tensor metadata and execution kernels should remain separate.
5. Shape, strides and offsets must be respected by operations.
6. Logical element counts must be distinguished from allocation capacity.
7. Every feature should include native C++ tests.
8. Python tests should be added where Python APIs are affected.
9. Backend-specific behavior must be tested on appropriate hardware.
10. Existing public APIs and compatibility should be preserved.
11. New features should be introduced in bounded milestones.
12. Performance optimization should be based on reproducible measurements.
13. Avoid speculative GPU abstractions before actual GPU implementation.
14. Preserve existing worktree changes; do not discard unrelated work.
15. Do not mark a milestone complete until its required validation is actually executed.

# 17. Baseline Assessment

LabNeura currently has a meaningful nD Tensor and CPU execution foundation.

The strongest completed architectural areas are:

- nD Tensor construction.
- Storage ownership and memory safety.
- Shape, strides and offsets.
- Shared-storage views.
- Broadcasting metadata.
- Generic arithmetic broadcasting.
- BOOL dtype.
- Generic and NEON comparisons.
- CPU backend dispatch.
- CPU threading infrastructure.

The most important unfinished areas are:

- AVX2 comparison runtime validation.
- Cross-backend comparison parity.
- Logical and selection operations.
- Reductions.
- Matrix operations.
- General multidimensional views.
- Broader SIMD broadcasting support.

LabNeura should therefore be considered an actively developing CPU-first Tensor computing library with a growing numerical operation set, rather than a complete numerical or machine learning framework.
